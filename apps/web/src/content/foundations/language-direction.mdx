## Treat language as context

Veli supports English and Dhivehi as application-level modes. The selected language determines content language, locale, reading direction, and the appropriate type stack.

| Language | Locale  | Direction |
| :------- | :------ | :-------- |
| English  | `en-GB` | `ltr`     |
| Dhivehi  | `dv-MV` | `rtl`     |

## Use the provider contract

Set language through `VeliProvider` so components receive a supported combination of locale and direction.

```tsx
<VeliProvider language="dv">
  <App />
</VeliProvider>
```

Do not pass direction independently from language unless a contained piece of authored content genuinely uses another writing direction.

## Mark content that uses another language

An untranslated English field can appear inside a Dhivehi interface. Keep its actual language with the selected value and set `lang="en"` and `dir="ltr"` on the text element carrying its `type-*` utility. The surrounding interface can stay Dhivehi. The same rule applies to Dhivehi content inside an English interface.

See [mixed-language typography](/foundations/typography/#mixed-language-content-and-english-fallbacks) for examples, inherited typography pitfalls and numeric content guidance. Veli does not infer the language of CMS values.

## Design logical layouts

Use logical properties such as `margin-inline-start`, `padding-inline`, and `inset-inline-end`. Directional icons should mirror only when their meaning depends on reading direction.

## Review real translations

Translated strings vary in length and rhythm. Test navigation, form labels, validation, tables, dates, and empty states with production-like English and Dhivehi content at every supported breakpoint.
